# v2.3.11 — Synthesis speed Phase 1 (batch limit + fallback visibility)

Production release for **Phase 1 orchestration hardening**: faster segment waves per browser kick, and clear visibility when synthesis falls back to the browser. Builds on v2.3.10 Phase 0 (env tuning, metrics, keep-tab-open UI).

**Operating mode unchanged:** browser tab open, background worker off, Opus audit off.

---

## Highlights

- **`SYNTHESIS_BATCH_LIMIT=8`** on API deploy — up to 8 ready segments claimed per `/synthesis/process` kick (was hard-capped at 4)
- **`synthesisDriver` on job results** — API returns `server` or `browser` so clients and logs can distinguish paths
- **Browser fallback warning** on the job detail view when server synthesis failed
- **`server_synthesis_fallback` log event** when the browser POSTs a synthesis result

---

## Phase 1.1 — Un-cap synthesis batch limit

### Problem
`processSynthesisBatch` forced `batchLimit: min(4, WORKFLOW_BATCH_LIMIT)` even when `WORKFLOW_BATCH_LIMIT=12`. Large jobs needed extra poll/kick rounds between segment waves.

### Change
- New env var **`SYNTHESIS_BATCH_LIMIT`** (default **4** in code, max **16**)
- `resolveSynthesisBatchLimit()` reads env at runtime and honors explicit `batchLimit` options
- Production release sets **`SYNTHESIS_BATCH_LIMIT=8`** alongside existing **`SYNTHESIS_CONCURRENCY=8`**

### Effect
For a job with 16 synthesis segments, each `/synthesis/process` kick can now start up to **8** partial segments in parallel (subject to concurrency), instead of 4 — roughly halving segment-wave round-trips in browser-driven mode.

### Files
- `api/_lib/synthesis.js` — `resolveSynthesisBatchLimit()`, wired into `listReadySynthesisSegments`
- `api/_lib/queue.js` — `processSynthesisBatch` uses resolved limit (re-exported)
- `.github/workflows/release.yml` — API deploy env
- `README.md` — env var documented

## Phase 1.2 — Server vs browser synthesis visibility

### API
- **`GET /api/jobs/:id/result`** and synthesis process responses include **`synthesisDriver`**: `'server'` | `'browser'`
- `inferSynthesisDriver()` derives driver from stored warnings or assumes `server` when a server-saved opinion exists
- Browser **`POST /result`** with `synthesisDriver: 'browser'` logs:
  - `server_synthesis_fallback`
  - `synthesis_driver_browser_fallback` (legacy alias for existing log filters)

### UI
- Job result view shows a **red warning banner** when `synthesisDriver === 'browser'`:
  *Browser synthesis fallback — opinion generated in-browser because server-side synthesis was unavailable.*

### Files
- `api/_lib/jobs.js` — `inferSynthesisDriver()`
- `api/jobs/[...path].js` — `publicJobResult()`, fallback logging
- `public/index.html` — `renderJobResults()` banner

Set automatically on this release deploy (cumulative with v2.3.10):

| Variable | Value | Notes |
|----------|-------|-------|
| `OPUS_AUDIT_ENABLED` | `false` | Required — do not enable |

| **`SYNTHESIS_BATCH_LIMIT`** | **`8`** | **New in v2.3.11** — segments per process kick |

| `SYNTHESIS_PARTIAL_MAX_TOKENS` | `4000` | Partial summary cap |

## Observability

| Event | When |
|-------|------|
| `synthesis_batch_complete` | Each `/synthesis/process` batch — check `completedInBatch` vs segment count |
| `synthesis_merge_complete` | Final opinion saved — `synthesisDurationMs`, `segmentCount`, `warningFlags` |
| `server_synthesis_fallback` | Browser POST `/result` after server synthesis failed |
| `synthesis_driver_browser_fallback` | Same as above (legacy event name) |

**Healthy durable jobs:** `synthesisDriver: server` on results; **no** fallback log events.
