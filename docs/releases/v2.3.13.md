# v2.3.13 — Synthesis speed Phase 3 (merge input/output optimization)

Production release for **Phase 3 merge optimization**: tighter partial summaries, Gemini compaction before Sonnet merge, Anthropic prompt caching on merge input, and opt-in multi-segment planning for large single-pass jobs. Builds on v2.3.12 Phase 2 (streaming final merge), v2.3.11 Phase 1 (batch limit + fallback visibility), and v2.3.10 Phase 0 (env tuning, metrics, keep-tab-open UI).

**Operating mode unchanged:** browser tab open, background worker off, Opus audit off.

---

## Highlights

- **Table-shaped partial synthesis prompt** — denser Gemini segment output (chain rows, defects, running balance)
- **Gemini compaction pass** — when ≥6 segments or merge input ≥40k tokens, Flash compacts summaries before Sonnet final merge
- **Anthropic prompt caching on merge** — segment summary block cached when ≥1024 tokens; `synthesis_prompt_cache_usage` log event
- **Opt-in large-job multi-segment planning** — `SYNTHESIS_LARGE_JOB_MULTI_SEGMENT` (default off) forces Gemini partials instead of one Sonnet pass on bulk jobs
- **Quality gates unchanged** — Sonnet still writes the final opinion; `validateFinalOpinion` runs before `saveJobResult`; compaction is input compression only

---

## Phase 3.1 — Tighter partial synthesis prompt

### Problem
Partial segment summaries included prose between chain links. That inflated Sonnet merge input on multi-segment jobs without adding legal substance.

### Change
`PARTIAL_SYNTHESIS_PROMPT` now requires strict table output:

| Section | Format |
|---------|--------|
| `## CHAIN ROWS` | Pipe table per instrument (date, parties, interest, running balance) |
| `## DEFECTS` | Pipe table (issue, curative, source doc) |
| `## RUNNING BALANCE` | Pipe table at segment end |

No preamble prose between sections. Final ownership determination remains Sonnet’s job at merge time.

### Effect
Shorter, denser partial summaries → smaller Sonnet merge input → faster final merge time-to-first-token and completion.

### Files
- `api/_lib/synthesis.js` — `PARTIAL_SYNTHESIS_PROMPT`, `validateSegmentSummary()`

---

## Phase 3.2 — Gemini compaction before final merge

### Problem
Jobs with many segments (6+) or very large merge input sent all partial summaries directly to Sonnet. Merge wall-clock scaled with input size even after Phase 2 streaming improved perceived latency.

### Why Gemini (not Sonnet) for compaction
Compaction is **structured compression** — merge N table-shaped partials into one dense scaffold. Gemini Flash is fast and cheap for that step. Sonnet still writes the final legal opinion prose from the scaffold.

### When
`SYNTHESIS_COMPACTION_ENABLED` (default **on** in code; **true** on production deploy) and either:

- Segment count ≥ `SYNTHESIS_COMPACTION_MIN_SEGMENTS` (default **6**), or
- Estimated merge input ≥ `SYNTHESIS_COMPACTION_MIN_MERGE_TOKENS` (default **40000**)

Small/medium jobs skip compaction and merge partials directly — same path as v2.3.12.

### Flow
```text
N partial summaries
  → Gemini Flash (COMPACTION_SYNTHESIS_PROMPT)
  → single compact scaffold
  → Sonnet final merge (streaming when SYNTHESIS_STREAM_ENABLED=true)
  → validateFinalOpinion
  → saveJobResult
```

### Quality safeguards
- Compaction output is **not** saved as the final opinion
- Sonnet merge + validation gate unchanged from prior releases
- Warning flag `merge_compaction_applied` on affected jobs for monitoring
- Disable with `SYNTHESIS_COMPACTION_ENABLED=false` if golden jobs regress

### Observability
- Log: `synthesis_merge_compaction_start` — `segmentCount`, `mergeInputBytes`
- Warning: `merge_compaction_applied`

### Files
- `api/_lib/synthesis.js` — `COMPACTION_SYNTHESIS_PROMPT`, `compactSegmentSummariesForMerge()`, `shouldCompactBeforeMerge()`

## Phase 3.3 — Prompt caching on merge user content

### Change
Final Sonnet merge requests wrap the segment summary block in Anthropic `cache_control: { type: 'ephemeral' }` when content ≥1024 tokens (`SYNTHESIS_MERGE_CACHE_MIN_TOKENS`).

Header (preamble, tract, context) stays uncached; the large repeatable segment block is cached.

### Benefit
Merge retries and follow-ups can hit cache on the segment prefix — lower latency and cost on repeated merge attempts.

### Observability
- Log: `synthesis_prompt_cache_usage` — `cacheReadInputTokens`, `cacheCreationInputTokens`, `mergeCached`

### Files
- `api/_lib/anthropic-request.js` — `buildMergeUserMessageContent()`, `estimateTextTokens()`
- `api/_lib/synthesis.js` — `cacheMergeSegments` on final merge calls

---

## Phase 3.4 — Large-job multi-segment planning (opt-in)

### Problem
Jobs planned as a single segment send all raw abstracts to Sonnet with no Gemini partial compression.

### Change
When **`SYNTHESIS_LARGE_JOB_MULTI_SEGMENT=true`** and abstract count ≥ `BULK_JOB_MIN_ABSTRACTS`, replan with standard chunk size (`forceChunkSize`) to produce multiple Gemini partial segments instead of one Sonnet single-pass.

Opt out: **`SYNTHESIS_FORCE_SINGLE_PASS=true`**

### Deploy default
**Not enabled on production release deploy** — leave unset/false until golden-job quality sign-off. No behavior change for existing production jobs until explicitly enabled.

### Files
- `api/_lib/synthesis.js` — `shouldForceMultiSegmentPlanning()`, `buildSynthesisChunks()` `forceChunkSize` override

## Production configuration (API service)

Set automatically on this release deploy (cumulative with v2.3.10–v2.3.12):

| Variable | Value | Notes |
|----------|-------|-------|
| `OPUS_AUDIT_ENABLED` | `false` | Required — do not enable |
| `SYNTHESIS_CONCURRENCY` | `8` | Parallel Gemini partial segments |
| `SYNTHESIS_BATCH_LIMIT` | `8` | Segments per process kick |
| `SYNTHESIS_STREAM_ENABLED` | `true` | Stream final merge (Phase 2) |
| **`SYNTHESIS_COMPACTION_ENABLED`** | **`true`** | **New in v2.3.13** — Gemini pre-merge compaction |
| `SYNTHESIS_COMPACTION_MIN_SEGMENTS` | `6` (code default) | Compaction segment threshold |
| `SYNTHESIS_COMPACTION_MIN_MERGE_TOKENS` | `40000` (code default) | Compaction input threshold |
| `SYNTHESIS_LARGE_JOB_MULTI_SEGMENT` | *(unset)* | Opt-in only — **not** set on deploy |
| `SYNTHESIS_MAX_TOKENS` | `5000` | Final Sonnet output cap |
| `SYNTHESIS_PARTIAL_MAX_TOKENS` | `4000` | Partial summary cap |
| `ABSTRACTION_ESCALATION_ENABLED` | `false` | Skip Sonnet re-reads on low-confidence abstracts |

**Worker service (unchanged):** `WORKER_DISABLED=true`, scale-to-zero, `OPUS_AUDIT_ENABLED=false`.

**Local / dev:** compaction on by default in code; streaming and multi-segment forcing follow their own env flags.

## Ops checklist after deploy

1. Run a 200+ doc job with tab open; confirm streaming preview still appears during final merge (Phase 2 unchanged)
2. Compare `synthesis_merge_complete.inputTokens` to v2.3.12 baseline — expect lower on multi-segment jobs
3. Confirm `merge_compaction_applied` / `synthesis_merge_compaction_start` only on jobs with ≥6 segments or very large merge input
4. Spot-check final opinion quality on 1–2 golden jobs — defects, gaps, and ownership tables still present
5. Monitor `final_validation_failed` rate — should not increase vs v2.3.12
6. On merge retry, check for `synthesis_prompt_cache_usage` with `cacheReadInputTokens > 0`
7. Do **not** enable `SYNTHESIS_LARGE_JOB_MULTI_SEGMENT` until explicit quality sign-off

**Rollback lever:** set `SYNTHESIS_COMPACTION_ENABLED=false` on API service to restore v2.3.12 merge input path without code rollback.
